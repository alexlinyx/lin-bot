# LinBot: A Student Query Assistant

*A step-by-step guide to building a real technical project with Claude.*

This repository is two things at once. It's a working software project — a backend service that answers student questions using a Claude model — and it's a **teaching document**. Each section is written so that a student can follow along, understand *why* each decision was made, and reproduce the buildout themselves. As the project grows, we append a log at the end of each work session (see `Session Log` below) so you can see how a real project accumulates over time rather than appearing fully formed.

If you are reading this to learn: don't just copy the commands. Read the "Why" callouts. The goal is for you to be able to build the *next* project without a guide.

---

## What we're building

A small web service — call it **LinBot** — that receives a student's question over an HTTP endpoint and returns an answer generated by a Claude model. Think of it as the backend a course website or a Discord bot would call.

In this first pass, the scope is deliberately narrow:

- A single HTTP endpoint that accepts a question and returns an answer.  
- A connection to a Claude model to generate that answer.  
- Basic guardrails: input validation, a system prompt that shapes the assistant's behavior, and simple rate limiting.

**Explicitly out of scope for the first pass** (we'll revisit these later): scheduling/calendar features and any mailbox/email functionality. We're naming them here so future-you knows they were a deliberate omission, not an oversight.

## A decision you have to make before writing any code

You said you want to *"use a Claude subscription plan to call via an API endpoint."* This is the single most important thing to get right, and it's a common point of confusion, so we're putting it front and center.

**Why this matters:** A paid Claude subscription (Pro or Max) and the Claude *API* are **separate products with separate billing**. Your Pro/Max subscription gives you access to Claude through the web, desktop, and mobile apps, and to Claude Code in your terminal. It does **not** hand you an API key you can point a backend server at. The developer API (via the Claude Console) is billed per token and is a different account entirely. Many first projects stall right here because someone assumed the $20/month subscription would power their app's backend. It won't, at least not directly.

Given that, you have two legitimate routes. Pick based on your constraints:

### Route A — Claude Developer Platform (API key) — *recommended for a real service*

You create an account on the Claude Console, generate an API key, and your backend calls the standard `/v1/messages` endpoint. Billing is pay-as-you-go, per token.

- **Pros:** Purpose-built for exactly this — a backend serving many users' queries. Predictable, documented, scales cleanly. This is how production apps are built.  
- **Cons:** Separate from your subscription; you pay per token on top of any subscription you hold.

### Route B — Claude Agent SDK on your subscription — *fits the letter of your request*

Anthropic lets Pro/Max/Team/Enterprise subscribers use the **Claude Agent SDK** (and the headless `claude -p` command) against a monthly **Agent SDK credit** that comes with the plan, rather than requiring a separate API-billed key. Your backend shells out to / wraps the Agent SDK to answer queries.

- **Pros:** Uses your existing subscription's included credit. Closest match to "use my subscription plan to serve queries."  
- **Cons:** The Agent SDK credit is sized for individual experimentation and light automation, not high-volume production traffic. Once the credit is exhausted, requests either stop or fall through to standard API rates (only if you've enabled usage credits). For a class-wide, always-on service, Anthropic itself points you back to Route A.

**Our recommendation for this guide:** We build against **Route A (the API)** because it teaches the general, transferable pattern for putting an LLM behind a backend — the skill you'll reuse everywhere. We'll structure the code so the model-calling layer is isolated behind one interface, meaning you could swap in Route B later by changing a single module. `ROADMAP.md` describes exactly where that seam lives.

*(Product and billing details change. Before you spend money, verify current pricing and plan terms at the official pricing page and the Claude Console.)*

## Prerequisites

Before session 1, make sure you have:

- A recent version of your language runtime installed (this guide uses Python 3.11+, but the architecture is language-agnostic).  
- A code editor and a terminal you're comfortable with.  
- Git, and a GitHub (or similar) account for version control.  
- For Route A: a Claude Console account and an API key, stored as an environment variable — **never** committed to the repo.  
- For Route B: an active Pro/Max/Team/Enterprise subscription and the Claude Agent SDK installed.

**Why an environment variable:** Secrets in source control leak. Anyone who can see your repo — including its entire git history — can see a committed key. We store keys in the environment and read them at runtime. This habit is non-negotiable in real projects.

## Session Log

*Each work session appends one entry here. Newest at the bottom. This is the running history of the project — treat it as a lab notebook.*

### Session 1 — Project framing and architecture (this session)

**Goal:** Establish the project, decide the core architecture, and write the two guiding documents before any code.

**What we worked on:**

- Defined the project scope: a single-endpoint backend that answers student questions via a Claude model. Scheduling and mailbox functionality explicitly deferred.  
- Resolved the central architectural question — subscription vs. API — and documented both routes (A: Developer Platform API key; B: Agent SDK on a subscription), recommending Route A while designing the code so Route B remains a drop-in swap.  
- Established the secret-handling convention (environment variables, never committed).  
- Authored `README.md` (this file) as the guide \+ session log, and `ROADMAP.md` as the technical architecture.

**Decisions recorded:**

- Model-calling logic will live behind a single `model` interface so the underlying provider/route can change without touching the server layer.  
- First pass ships the query endpoint only; no persistence, no scheduling, no email.

**Next session:** Scaffold the repository and stand up a "hello world" HTTP endpoint that returns a canned response — no model call yet. Proving the plumbing before adding the model keeps failures easy to diagnose.

### Session 2 — Provider decision and a bigger end goal

**Goal:** Choose the inference provider for the first pass, and — as it turned out — reckon with a larger ambition that reshapes the project's scope.

**What we worked on:**

- Surveyed cheap cloud inference options and compared gateways (OpenRouter vs. Hugging Face's three products) against going direct to a single provider.  
- Settled on **base DeepSeek V4 Flash via its direct API** for pass one: cheapest, simplest, and — since DeepSeek's API accepts both OpenAI- and Anthropic-style formats — easy to integrate. Established that for a single known model, going direct beats paying a gateway's routing margin.  
- Surfaced the real end goal: **host our own fine-tuned model**, released as gradual, measured iterations deployed on Hugging Face Inference Endpoints. This promotes the project from a personal side project to a research direction.  
- Worked through why "fine-tune eventually" shouldn't mean "route through HF now": HF is the natural home for the *training* side, but for *serving*, a single known model is cheapest direct. The base-model phase also generates the real question data and failure cases a good fine-tune depends on.  
- Designed the staged-rollout architecture — canary traffic split, baseline fallback, per-request model attribution — and the evaluation harness needed to tell whether each iteration actually beats the baseline.  
- Generalized the roadmap from Claude-specific (Route A/B) to provider-agnostic, and added §9 (model rollout strategy), §10 (evaluation harness), and §11 (updated scope) to `ROADMAP.md`.

**Decisions recorded:**

- Pass one serves base DeepSeek V4 Flash, direct API, behind the existing `generate_answer()` seam.  
- End goal is a self-hosted fine-tuned model on HF Inference Endpoints, rolled out in phases (baseline → canaried v1 → iterate), never as a hard swap.  
- Every request will be logged with its answer and the model that produced it — this is simultaneously the fine-tuning corpus and the evaluation ground truth.  
- The earlier Claude routes remain valid implementations of the same seam but are not the active plan.  
- Scheduling and mailbox remain deferred.

**Why this session mattered:** The scope expanded, but the original architecture absorbed it without a rewrite — the single model seam is exactly what lets a hosted API today become a self-hosted fine-tuned model tomorrow. That's the payoff of the isolation decision from Session 1, and a lesson worth internalizing: good early boundaries let a project's ambitions grow without its foundation cracking.

**Next session:** Scaffold the repository and stand up the "hello world" endpoint (build-sequence step 1), still with no model call. The provider decision doesn't change the plumbing-first order.

### Session 3 — The whole first pass, built and verified

**Goal:** Execute the build sequence — and, since the router/canary architecture was already designed, build it too while the design was fresh.

**What we worked on:**

- Made the remaining infrastructure decisions: **FastAPI** for the server layer (async-native — requests spend their time waiting on the provider's network, so one small instance handles our concurrency trivially), **Postgres** for the request log (it's future training data; a flat file doesn't scale with that ambition), and **Railway (paid, always-on) \+ managed Postgres** for hosting ("always up" rules out sleeping free tiers; a VPS saves almost nothing at this scale while adding ops burden).  
- Built the entire pass-one build sequence (steps 1–7): scaffold, config with loud startup failure, fake provider, Postgres request logging with alembic migrations, real DeepSeek client, guardrails (400/429/502 exactly per §2), and a 21-test suite with CI.  
- Built the §9 rollout machinery ahead of schedule: the `ModelRouter` with `CANARY_PERCENT` weighted split and fallback chain, plus the HF Inference Endpoint provider. With no candidate configured it degenerates to "call the primary," so pass one and Phase 2 share one code path — Phase 2 becomes a config change, not a code change.  
- Noticed DeepSeek and HF TGI/vLLM endpoints both speak the OpenAI chat-completions format, so both providers are one shared client (`openai_compat.py`) with different settings.  
- Added the eval harness skeleton (`eval/build_eval_set.py`, `eval/compare.py`) and `DEPLOY.md` with the Railway runbook.

**Decisions recorded:**

- FastAPI \+ uvicorn; Postgres via SQLAlchemy async \+ psycopg; alembic migrations run automatically before server start.  
- Request logging must never break the product: logging happens after the response (or is swallowed with an app-log entry if the insert fails). Losing one corpus row is acceptable; failing a student's request is not.  
- The rate limiter is in-process on purpose — exact and free on a single always-on instance; swap for a shared store only if we ever run replicas.

**A bug worth remembering:** our first error-path implementation attached the failure log to FastAPI's `BackgroundTasks` — but background tasks only run when attached to a *returned* response, and the error path raises an exception instead. The test suite caught it: 502s were served correctly but never logged. Lesson: background work tied to a response object silently disappears on paths that don't return one.

**Verified:** all 21 tests green; live server boots with the fake provider, answers `/ask`, returns the §2 error contract exactly, and logs each request with model attribution; missing config refuses to boot with a readable message.

**Next session:** Push to GitHub, deploy to Railway per `DEPLOY.md` with a real `DEEPSEEK_API_KEY`, and confirm the first real model answers land in the production `requests` table. Then start accumulating Phase 1 traffic.

### Session 4 — Deployed to production, and a fourth provider

**Goal:** Get the service live on Railway, and add an Anthropic (Claude) provider for testing.

**What we worked on:**

- Pushed the repo to GitHub (`alexlinyx/lin-bot`); CI runs lint \+ tests on every push.  
- Deployed to Railway: the app service and a managed Postgres in one project (an initial separate-project Postgres couldn't use Railway's private networking — the fix was a Postgres *inside* the app's project, wired via a `${{Postgres.DATABASE_URL}}` reference variable). Public URL: `https://lin-bot-production.up.railway.app`.  
- **Verified the deployed stack plumbing-first**: booted with `PROVIDER=fake` before spending any tokens — health check, a logged `/ask` round-trip into production Postgres with model attribution, migrations auto-applied on boot, and the loud config failure confirmed in the crash logs from the first (unconfigured) deploy. The design worked exactly as intended: the crashed first deploy *was* the fail-loudly behavior.  
- Added an **Anthropic provider** (`PROVIDER=anthropic`). Unlike DeepSeek and HF endpoints, Anthropic's Messages API is not OpenAI-compatible, so this one uses the official `anthropic` SDK rather than the shared OpenAI-style client — a nice illustration that the seam accommodates providers with entirely different wire formats. Claude's adaptive thinking is enabled; safety-classifier refusals are treated as provider errors so the router's fallback path can catch them.

**Decisions recorded:**

- Default Claude model is `claude-haiku-4-5` (fast and cost-effective for testing), configurable via `ANTHROPIC_MODEL_NAME`. Adaptive thinking is sent only for Claude 4.6+ models, which Haiku 4.5 is not.  
- A provider refusal (HTTP 200 with `stop_reason: "refusal"`) maps to the same `ProviderError` as a network failure — the student gets a fallback answer or a clean 502, never a half-empty response.

**Next session:** Set a real provider API key in Railway, flip `PROVIDER` off `fake`, and verify the first real model answer lands in the production `requests` table. Then start accumulating Phase 1 traffic.
